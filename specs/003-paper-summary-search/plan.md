# Implementation Plan: Paper Reading Experience (Search, Details, Summaries, Bookmarks, Recommendations)

**Branch**: `003-paper-summary-search` | **Date**: 2026-05-23 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/003-paper-summary-search/spec.md`

## Summary

Deliver MVP `#5` (AI summaries via Gemini), `#7` (search and filter), `#8` (paper detail view) as one backend-focused iteration that layers a coherent reading experience on top of `002-topic-subscription`'s already-populated catalog. Bookmarks reuse `001-user-auth`'s existing `Favorite` table (no schema change to `Favorite`). Recommendations are scored by **metadata similarity** (shared topics, shared authors, category overlap, lexical similarity of title/abstract) — no embedding cost in v1.

Six user stories, summarised:

- **US1 (P1)** — Search papers across the user's own catalog by free-text query.
- **US2 (P2)** — Per-paper detail view with full metadata, the bullet summary, the bookmark control, and the related-papers list.
- **US3 (P2)** — Automatic bullet-point summaries (3–5 bullets) generated by Gemini as part of `002`'s ingestion cycle; one summary per paper shared across all users.
- **US4 (P2)** — Bookmark / unbookmark from search, detail view, or per-topic view; favourites view lists all the user's bookmarks across topics. Bookmarks reuse `001`'s `Favorite` table; bookmarks persist even when the source topic is deleted.
- **US5 (P3)** — Filter search results by topic, date range, and author with AND semantics.
- **US6 (P3)** — Metadata-based "related papers" surface on the detail view, scoped to the requesting user's own catalog.

Frontend integration is **deferred** for this iteration — per the project's working agreement, the FE reorg is owned separately by another teammate. This plan ships only the backend service, schema, REST contracts, and operator quickstart. The contracts here are the FE handoff.

## Technical Context

**Language/Version**: TypeScript 5.8 strict on both frontend and backend; Node.js 20+ for the backend runtime.

**Primary Dependencies** (additions beyond what `001` + `002` already installed):

- `@google/generative-ai` — official Google Gemini SDK for the Node runtime, used by `external/gemini.client.ts` for chat-completion / generateContent calls (Constitution Principle IV: AI access MUST be isolated in an AI service).
- (No new dependency for full-text search — MySQL's built-in `FULLTEXT` index on `Paper.title` and `Paper.abstract` is sufficient for the SC-001 latency target at < 1k papers per user.)
- (No new dependency for similarity — metadata similarity is computed inline in `recommendations.service.ts` using existing Prisma queries plus a small in-process scoring routine.)
- Existing from `001` + `002`: `express`, `@prisma/client`, `prisma`, `jsonwebtoken`, `zod`, `cors`, `dotenv`, `tsx`, `bcryptjs`, `node-cron`, `fast-xml-parser`.

**Storage**: MySQL 8.4 via Prisma, same container as `001` + `002`. New table: `PaperSummary`. No schema changes to `User`, `Favorite`, `TrackedTopic`, `Paper`, `TopicPaperMatch`, `FetchCycle`. New migration: `0003_paper_summaries` (additive only; adds `PaperSummary` table and a `FULLTEXT` index on `Paper(title, abstract)`).

**Testing**: Manual quickstart walkthrough (`quickstart.md`), matching `001` and `002`'s precedent. Automated tests remain out of scope until a follow-up hardening pass.

**Target Platform**: same as `002` — Express REST API on port 4000, MySQL 8.x via connection string. Local development on macOS/Linux; production deployment is out of scope.

**Project Type**: Web application (backend-only this iteration; frontend deferred).

**Performance Goals**: Per the `001` + `002` precedent ("skip perf for now"), no perf benchmarking required. SC-001 (≤ 2 s for search over 1k papers) is comfortably met by indexed Prisma queries against a single MySQL table. SC-004 (summary coverage within one ingestion cycle) and SC-006 (≤ 1 AI call per paper) are correctness properties enforced by schema + service logic, not perf goals. The Gemini rate limit is the hard upstream constraint; the summarisation service respects it via per-cycle caps and serialised calls.

**Constraints**:

- Gemini rate limits and cost — addressed by per-cycle summary cap (`AI_PER_CYCLE_SUMMARY_CAP`), one-call-per-paper guarantee (`PaperSummary.@@unique([paperId])`), and graceful retry on transient failure. Gemini's free tier (15 RPM / 1500 RPD for `gemini-2.0-flash` as of v1) is the operative ceiling; the per-cycle cap default is sized to fit comfortably below it.
- Catalog-scope privacy invariant (FR-004, FR-009, FR-031) — every endpoint that touches paper data filters by `userId = req.userId` and joins through `TopicPaperMatch`; recommendations honour the same scope.
- Bullet format integrity (FR-022) — the AI response is parsed into a typed `string[]` and validated by Zod before persistence; malformed responses are stored as `not_summarisable` rather than displayed.
- Bookmarks reuse `001`'s `Favorite` table (`paperId` is `VARCHAR(64)`; we interpret it as `Paper.id` cuid going forward). Existing test fixtures from `001` that wrote arbitrary `paperId` strings are unaffected — they remain valid favourites; they simply won't join to a real `Paper` row.

**Scale/Scope**: Pre-MVP local development. Expected initial: < 100 users, up to ~20 tracked topics per user, ~50–200 papers per user catalog. Search over a single user's catalog stays in the hundreds of rows. The summarisation pipeline runs ~10–100 Gemini calls per ingestion cycle in worst case (capped by env config). Recommendations compute similarity inline over the user's catalog (hundreds of rows); no precomputed similarity table in v1.

**Structure Decision**: Extend the existing `/backend` service introduced by `001` and grown by `002`. Database access continues to flow exclusively through Prisma in repository modules. Controllers parse, services orchestrate, the Gemini SDK is the only new external dependency. The `ai.service.ts` wrapper is deliberately provider-agnostic so that the v1 Gemini choice can be swapped to OpenAI or another provider in the future without disturbing services / repositories / controllers above it (per the constitution's "Default AI Provider Selection" guidance, swap is a plan-level decision that stays inside `external/` + `services/ai.service.ts`). Summarisation hooks into `002`'s existing fetch cycle as a post-persistence step rather than running on its own schedule — this preserves Constitution Principle IV (one scheduler entry point) and ensures summaries arrive promptly after ingestion.

## Constitution Check (re-check after Phase 1 design)

Re-verified after data-model, contracts, and quickstart are written. No new violations introduced.

- **Layered architecture preserved**: contracts (HTTP shape) → controllers → services → repositories → Prisma; Gemini access stays in `external/gemini.client.ts` + `services/ai.service.ts`; the cron job continues to be a thin shell.
- **Data discipline preserved**: every new field has a Prisma model and a migration; the new `PaperSummary` table has a unique index on `paperId` enforcing FR-013 at the schema layer; foreign keys are explicit; `Favorite` is reused without schema change.
- **No `any`**; `unknown` lives only at the Gemini response boundary (typed by Zod after parse) and at HTTP request bodies (Zod-narrowed). Bullet parsing returns a `string[]` typed value or throws.
- **Endpoints are resource-oriented**; status codes documented per endpoint in `contracts/`.
- **Operator-facing knobs** (Gemini model choice, per-cycle cap, search and recommendation limits) are env vars, not embedded in code.
- **Scheduler entry point unchanged**: `002`'s `jobs/fetchCycle.job.ts` is the single scheduled job; this feature extends the *service* it calls, not the scheduler.
