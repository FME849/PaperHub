# REST Contract: Notification Preference + Unsubscribe

**Resource**: `EmailNotificationPreference` — one per user. Controls whether the user receives per-fetch-cycle digest emails.

**Base path**: `/api/notifications`

**Authentication**:

- `GET /api/notifications/preference` and `PUT /api/notifications/preference` **require** a valid JWT bearer token. Missing/invalid token → `401 Unauthorized`.
- `GET /api/notifications/unsubscribe` is **explicitly unauthenticated** (FR-012) — the unsubscribe link must work without login. Authorisation is established by HMAC token verification, not by session.

Error envelope (consistent with `001` / `002` / `003`):

```json
{ "error": "Human-readable message", "details": { /* optional */ } }
```

Status codes used: `200 OK`, `400 VALIDATION_FAILED`, `401 AUTH_REQUIRED`, `403 FORBIDDEN`, `404 NOT_FOUND`, `500 INTERNAL_ERROR`.

---

## `GET /api/notifications/preference` — read the current preference

Returns the requesting user's current preference. If the user has never set a preference, returns the default shape (`enabled: false`) without writing to the database.

### Request

```http
GET /api/notifications/preference
Authorization: Bearer <jwt>
```

No path or query parameters.

### Responses

**`200 OK`** — body:

```json
{
  "enabled": false,
  "lastChangedAt": "2026-05-26T10:14:00.000Z",
  "lastChangedVia": "SETTINGS_UI"
}
```

| Field            | Type                                              | Notes |
|------------------|---------------------------------------------------|-------|
| `enabled`        | `boolean`                                         | False unless the user has opted in. |
| `lastChangedAt`  | `string` (ISO-8601) \| `null`                     | `null` when the user has never set a preference (default shape). |
| `lastChangedVia` | `"SETTINGS_UI" \| "UNSUBSCRIBE_LINK" \| "SYSTEM"` \| `null` | `null` when the user has never set a preference. |

**`401 AUTH_REQUIRED`** — missing or invalid JWT.

---

## `PUT /api/notifications/preference` — update the preference

Idempotent. Upserts the user's preference and records `lastChangedVia = SETTINGS_UI`.

### Request

```http
PUT /api/notifications/preference
Authorization: Bearer <jwt>
Content-Type: application/json
```

```json
{ "enabled": true }
```

| Field     | Type      | Notes |
|-----------|-----------|-------|
| `enabled` | `boolean` | Required. Any other shape → `400 VALIDATION_FAILED`. |

### Responses

**`200 OK`** — body matches the `GET` shape with the new state:

```json
{
  "enabled": true,
  "lastChangedAt": "2026-05-26T10:14:32.117Z",
  "lastChangedVia": "SETTINGS_UI"
}
```

**`400 VALIDATION_FAILED`** — body missing, not JSON, or `enabled` is not a boolean.

```json
{ "error": "enabled must be a boolean", "details": { "field": "enabled" } }
```

**`401 AUTH_REQUIRED`** — missing or invalid JWT.

### Side effects

- Upserts `EmailNotificationPreference` for the user.
- Sets `lastChangedAt = now()` and `lastChangedVia = SETTINGS_UI`.
- Takes effect from the **next** fetch cycle (FR-010). Does NOT trigger any out-of-band digest send (FR-007).

## `GET /api/notifications/unsubscribe?token=<v1:base64url>` — one-click unsubscribe (no login)

Public endpoint that flips the user's preference to off and returns a simple confirmation page. Idempotent: repeated clicks always result in `enabled = false` and the same confirmation HTML.

### Request

```http
GET /api/notifications/unsubscribe?token=v1:aGVsbG8tdGhpcy1pcy1ub3QtcmVhbA
```

| Query param | Notes |
|-------------|-------|
| `token`     | HMAC-SHA-256 of `userId` keyed by `UNSUBSCRIBE_TOKEN_SECRET`, base64url-encoded, prefixed with `v1:`. Generated by `notifications.service.ts` when composing the digest email. See [research.md](../research.md) Decision 6. |

### Responses

**`200 OK`** — `Content-Type: text/html; charset=utf-8`:

A minimal, no-JS HTML page confirming the unsubscribe. Body MUST NOT disclose the user's identity (no email address, no display name) — anyone who clicks the link sees only the same generic confirmation. Example body shape:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>PaperHub — unsubscribed</title>
    <meta name="robots" content="noindex">
    <style>body{font-family:system-ui,sans-serif;max-width:32rem;margin:4rem auto;padding:0 1rem;color:#222}</style>
  </head>
  <body>
    <h1>You're unsubscribed</h1>
    <p>You will no longer receive PaperHub paper-digest emails. You can re-enable them anytime from your account settings.</p>
  </body>
</html>
```

**`400 VALIDATION_FAILED`** — token missing, malformed (no `v1:` prefix, bad base64url, wrong length), or HMAC verification fails. Body is a generic error page (same `Content-Type: text/html`); the error response MUST NOT disclose which check failed, to avoid token-shape probing.

```html
<!doctype html>
<html lang="en">
  <head><meta charset="utf-8"><title>PaperHub — invalid link</title></head>
  <body><h1>This unsubscribe link is invalid or expired.</h1>
  <p>If you'd like to stop receiving emails, please log in to PaperHub and update your notification preference.</p></body>
</html>
```

**`500 INTERNAL_ERROR`** — unexpected server error. Generic HTML page; same redaction discipline.

### Side effects

- On success, upserts `EmailNotificationPreference` for the user resolved from the token: `enabled = false`, `lastChangedVia = UNSUBSCRIBE_LINK`, `lastChangedAt = now()`.
- Idempotent: clicking twice flips `enabled` to `false` both times (it's already `false` on the second click) and re-renders the same `200` page (FR-012; spec edge case "clicked more than once").
- If the user has already re-enabled the preference via authenticated settings (spec edge case "clicked after re-enabling"), the unsubscribe still wins — `enabled` is set to `false` unconditionally. The user can re-enable from settings again afterwards.
- Recorded in `EmailNotificationPreference.lastChangedVia` so subsequent renders of the in-app settings page can show "you were unsubscribed via email on Y date".

### Security notes

- The endpoint MUST NOT issue or extend any session cookie. The response includes no `Set-Cookie` header.
- The endpoint MUST NOT redirect to an authenticated page (which would expose login state and create an open-redirect surface).
- The token is **long-lived by design** (FR-012; research.md Decision 6); short-lived tokens would silently break old digest emails in user inboxes.
- `Content-Type: text/html` is correct for this endpoint; the rest of `/api/*` is JSON, but this surface is rendered directly in the user's browser from a delivered email.

## Cross-cutting

- The two preference endpoints (`GET` and `PUT`) live behind the same `authenticate` middleware as the rest of `/api/users`, `/api/topics`, etc. (`001`'s precedent).
- The unsubscribe endpoint sits on the same router (`notifications.routes.ts`) but is mounted **before** the `authenticate` middleware in the router definition, so it does not require a token. The router is mounted at `/api/notifications` from `server.ts`.
- All three endpoints log via the existing `requestLogger` middleware; the unsubscribe endpoint's log line MUST NOT include the raw `token` value (truncate to `v1:…` in logs).
- Rate limiting is out of scope for v1 across the whole project; if added later, the unsubscribe endpoint warrants a per-IP cap to deter token-shape brute force.
